# Буфер платёжных вебхуков: HTTP-шлюз + Redis + n8n

Набор к ролику «Буфер платёжных вебхуков: спасаем заказы от 502 и падений сервера». Лёгкий шлюз принимает вебхук платёжного сервиса, целиком (с заголовками и подписью) кладёт его в очередь Redis и только после этого отвечает 200. Сценарий n8n забирает оплаты из очереди по одной и отдаёт их вашей системе в темпе, который она выдержит. Если система заказов упала, оплаты ждут в очереди, а не пропадают. Без абонентской платы: платите только за VPS.

## Что внутри
| Файл | Для чего |
|---|---|
| `docker-compose.yml` | шлюз, Redis (журнал AOF), n8n и Caddy с HTTPS (профиль `https`) |
| `gateway/` | исходники шлюза: `app.py`, `Dockerfile`, `requirements.txt`, `test_app.py` (7 юнит-тестов на заглушке Redis) |
| `webhook_buffer_workflow.json` | шаблон n8n: безопасная вычитка очереди (проверка дубля, возврат в очередь при ошибке, список `webhooks:dead`) |
| `Caddyfile` | вход по HTTPS: наружу отдаются только `/hook/*` и `/health` |
| `.env.example` | пример файла настроек |
| `Инструкция.txt` | пошаговая инструкция для новичка и честные ограничения |

## Как это работает
1. Платёжный сервис шлёт `POST /hook/<провайдер>?token=...` на шлюз.
2. Шлюз кладёт конверт (тело, base64 тела, заголовки) в список Redis `webhooks:in` командой `LPUSH`. Только после успешной записи отвечает 200 (для Robokassa `OK<InvId>`). Если Redis недоступен, отвечает 503: платёжный сервис повторит доставку.
3. Сценарий n8n каждые 30 секунд берёт оплаты из хвоста списка (`RPOP`, порядок FIFO) по одной с паузой 0,3 с, пропускает уже обработанные (ключ `seen:<id>` на 7 суток) и отдаёт новые вашему обработчику.
4. Ошибка отдачи: оплата возвращается в очередь и сценарий останавливается до следующего запуска; после 5 неудач вебхук уходит в `webhooks:dead`.
5. Длину очереди видно командой: `docker compose exec redis redis-cli LLEN webhooks:in`.

## Быстрый старт
1. Нужны отдельный VPS с Docker и Docker Compose, домен с A-записью на IP VPS и открытые порты 80 и 443.
2. Скопируйте `.env.example` в `.env`, впишите `DOMAIN` и замените `WEBHOOK_TOKEN`.
3. `docker compose --profile https up -d --build`.
4. Откройте n8n по SSH-туннелю, импортируйте `webhook_buffer_workflow.json`, создайте учётные данные Redis (хост `redis`, порт 6379), впишите адрес своего обработчика.
5. Укажите в кабинете платёжного сервиса адрес `https://<домен>/hook/<провайдер>?token=<токен>`.

Аренда VPS: [Timeweb Cloud](https://timeweb.cloud/r/nf413716) (партнёрская ссылка, автор получает вознаграждение; условия на сайте, проверяйте актуальные).

## Честные ограничения
- Стек автор **на живом VPS не запускал**, сборку образа шлюза и сценарий в живом n8n не проверял. Шлюз проверен только юнит-тестами с заглушкой Redis (`python gateway/test_app.py`). Образ n8n указан как `latest`: закрепите версию после первого запуска.
- Время ответа шлюза «пара миллисекунд» это ориентир, не замер: замерьте на своём сервере.
- Сроки повторов платёжных сервисов (ЮKassa до 24 часов, Stripe до ≈ 3 суток) взяты из сторонних источников: сверьте с официальной документацией.
- Шлюз только принимает и хранит. Что оплата настоящая, подтверждает ваш обработчик: ЮKassa по найденным данным не подписывает тело (проверяйте платёж по API), Robokassa требует проверки контрольной суммы, подпись Stripe имеет допуск по времени (≈ 5 минут), поэтому при отложенной обработке подпись из очереди с допуском не пройдёт.
- Redis на одном сервере единая точка отказа; журнал AOF не заменяет резервную копию (правило 3-2-1). Доставка «минимум один раз»: обработчик должен быть идемпотентным. Проверка дубля в сценарии не атомарна и рассчитана на один экземпляр.
- Все суммы, номера и адреса в примерах вымышленные; сценарные «две секунды» и 502 в ролике не замеры и не статистика.
