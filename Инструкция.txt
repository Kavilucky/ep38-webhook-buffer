БУФЕР ПЛАТЁЖНЫХ ВЕБХУКОВ: HTTP-ШЛЮЗ + REDIS + N8N (эпизод 38)
=============================================================

ЧТО ВНУТРИ АРХИВА
- docker-compose.yml             стек: шлюз + Redis + n8n (+ Caddy с HTTPS по профилю https)
- gateway/                       исходники шлюза (app.py, Dockerfile, requirements.txt, test_app.py)
- Caddyfile                      вход по HTTPS: наружу отдаются только /hook/* и /health
- .env.example                   пример файла настроек
- webhook_buffer_workflow.json   шаблон n8n: безопасная вычитка очереди Redis
- Инструкция.txt                 этот файл

ЗАЧЕМ ЭТО НУЖНО
Когда сервер перегружен (распродажа, много оплат), ваш обработчик отвечает платёжному сервису ошибкой 502 или не успевает. Платёжный сервис повторяет доставку ограниченное время (по найденным данным: ЮKassa до 24 часов, Stripe до трёх суток, проверяйте в документации) и потом перестаёт: оплаченный заказ остаётся без статуса.
Шлюз ставится перед сайтом. Он принимает вебхук, целиком (с заголовками и подписью) кладёт его в очередь Redis и только после этого отвечает 200. n8n забирает оплаты из очереди по одной с паузой и отдаёт их вашей системе в том темпе, который она выдержит. Если ваша система упала, оплаты ждут в очереди.

ЧТО НУЖНО ЗАРАНЕЕ
1. VPS с Docker и Docker Compose (Ubuntu 22.04 или новее, от 1 ГБ ОЗУ). Аренда: Timeweb Cloud https://timeweb.cloud/r/nf413716
   Это партнёрская ссылка: автор получает вознаграждение. Условия (бонус до 2000 ₽, тариф от ~490 ₽/мес) указаны на момент записи по данным автора, не проверены: смотрите актуальные на сайте.
2. Домен или поддомен для вебхуков (например, hooks.вашдомен.ru) с A-записью на IP VPS; открытые порты 80 и 443.
3. Адрес обработчика заказов в вашей системе (куда n8n будет отдавать оплаты).

ЗАПУСК ШАГ ЗА ШАГОМ
1. Подключитесь к VPS по SSH, создайте папку и скопируйте в неё все файлы архива (с папкой gateway).
2. Переименуйте .env.example в .env. Впишите DOMAIN и замените WEBHOOK_TOKEN на длинную случайную строку.
3. Запустите: docker compose --profile https up -d --build
4. Проверьте контейнеры: docker compose ps (шлюз, redis, n8n, caddy в состоянии running).
5. Проверьте шлюз на самом сервере: curl -i http://127.0.0.1:8080/health (ожидается 200 ok).
6. Отправьте тестовый вебхук: curl -i -X POST "http://127.0.0.1:8080/hook/test?token=ВАШ_ТОКЕН" -d '{}'  (ожидается 200 OK).
7. Посмотрите очередь (redis-cli внутри контейнера):
   docker compose exec redis redis-cli LLEN webhooks:in        сколько оплат ждёт
   docker compose exec redis redis-cli LRANGE webhooks:in 0 4   что лежит (хвост списка уйдёт в обработку первым)
   docker compose exec redis redis-cli LLEN webhooks:dead       сколько ушло в список ошибок
8. n8n открывается только с самого сервера. С вашего компьютера: ssh -L 5678:127.0.0.1:5678 user@сервер, затем http://localhost:5678 (создайте владельца).
9. В n8n: Workflows -> Import from file -> webhook_buffer_workflow.json. Создайте учётные данные Redis (хост redis, порт 6379, без пароля, Redis не опубликован наружу).
10. В узле «Отдать заказ вашей системе» замените адрес https://example.com/api/payments/webhook на адрес вашего обработчика.
11. Нажмите Execute Workflow: тестовый вебхук из шага 6 уйдёт на ваш адрес. Потом включите сценарий переключателем Active.
12. В кабинете платёжного сервиса укажите адрес уведомлений: https://hooks.вашдомен.ru/hook/yookassa?token=ВАШ_ТОКЕН (для Stripe: /hook/stripe, для Robokassa: /hook/robokassa). Адрес и способ указания проверяйте в документации сервиса.

КАК ЭТО РАБОТАЕТ
- Шлюз отвечает 200 только после успешной записи в Redis. Если Redis недоступен, шлюз отвечает 503: платёжный сервис повторит доставку, и платёж не потеряется молча.
- Для Robokassa ответ шлюза: OK<InvId>, как требует её документация.
- Сценарий n8n каждые 30 секунд достаёт оплаты по одной, пропускает уже обработанные (ключ seen:<id> на 7 суток), отдаёт новые вашей системе и ждёт 0,3 с. Ошибка отдачи: оплата возвращается в очередь, после 5 неудач уходит в список webhooks:dead.

ВАЖНО: ПРОВЕРКА ПОДПИСИ И ДЕНЕГ (чтобы вас не обманули поддельным вебхуком)
- Шлюз только принимает и хранит. Подтверждение, что оплата настоящая, делает ВАШ обработчик.
- ЮKassa (по найденным данным): тело уведомления не подписывается; перед выдачей заказа запросите платёж по API ЮKassa и сверьте статус и сумму.
- Robokassa: проверяйте контрольную сумму (OutSum, InvId, Shp_*) по документации; при фильтрации по IP добавьте адреса, указанные в документации Robokassa.
- Stripe: подпись Stripe-Signature хранится в заголовках, но библиотеки проверяют допуск по времени (по умолчанию порядка 5 минут). При отложенной обработке из очереди подпись с допуском не пройдёт: получайте событие по API Stripe или проверяйте подпись в шлюзе. Проверьте в документации Stripe.

РЕЗЕРВНАЯ КОПИЯ (правило 3-2-1, обязательно)
- Очередь и журнал AOF лежат в томе redis-data. Redis с AOF переживает перезапуск, но это не резервная копия: при аварии диска очередь потеряется.
- Копия тома (узнайте имя тома: docker volume ls; обычно <папка>_redis-data):
  docker run --rm -v ИМЯ_ТОМА:/data -v "$PWD":/backup alpine tar czf /backup/redis-backup.tgz -C /data .
- Держите 3 копии, на 2 разных носителях, 1 вне сервера. Не удаляйте оригиналы, пока копия не проверена (распакуйте и убедитесь, что файлы на месте). Также копируйте том n8n-data (учётные данные и сценарии).

ЧЕСТНЫЕ ОГРАНИЧЕНИЯ (проверяйте актуальные условия сервисов)
- Автор НЕ запускал этот стек на живом VPS и не запускал сценарий в живом n8n. Шлюз проверен только юнит-тестами с заглушкой Redis (python gateway/test_app.py): 7 тестов, живой Redis и сеть не участвовали. Проверьте после запуска.
- Время ответа шлюза «за пару миллисекунд» это ориентир, не замер: замерьте сами (curl -w '%{time_total}').
- Расписание повторов платёжных сервисов (ЮKassa до 24 часов, Stripe до ≈ 3 суток) взято из сторонних источников: сверьте с официальной документацией.
- Redis на одном сервере это единая точка отказа; доставка «минимум один раз»: вебхук может прийти и быть обработан повторно, поэтому ваш обработчик должен быть идемпотентным (не создавать заказ дважды). Проверка дубля в сценарии не атомарна (Get, затем Set) и рассчитана на один экземпляр сценария.
- Порядок оплат при повторах не гарантируется. «Ядовитое» сообщение после 5 попыток уходит в webhooks:dead: разбирайте этот список вручную.
- Образ n8n указан как latest: после первого запуска закрепите конкретную версию.
- Все суммы, номера и адреса в примерах вымышленные.
